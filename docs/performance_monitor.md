# 性能监视器：读数从哪里来

打开设置中的性能监视器，再选择正在运行的游戏或程序。选择的是可执行文件名，不是固定 PID，因此程序重启后可以重新匹配。存在多个同名进程时，优先匹配带可见窗口的进程；不能保证区分两个同名游戏实例。

| 显示内容 | 数据来源 | 含义 |
| --- | --- | --- |
| FPS | PresentMon 2.3.1，Windows ETW | 所选进程主要交换链提交画面的频率，按事件时间戳计算约一秒窗口，不叠加多个交换链 |
| CPU | GetSystemTimes | 整机 CPU 使用率，不是本组件的 CPU 使用率 |
| GPU | PDH GPU Engine 性能计数器 | 同一 GPU 引擎各进程读数相加，再取所有 GPU 中最繁忙引擎的使用率，不把不同引擎直接相加 |
| 内存 | GlobalMemoryStatusEx | 整机已用物理内存及总物理内存，不是本组件的内存占用 |

FPS 不是桌面合成帧率、显示器标称刷新率，也不保证等于实际呈现或插帧后的帧率。暂停渲染、最小化、不支持的呈现路径或没有有效帧事件时显示“—”。GPU 性能计数器依赖系统和显卡驱动的支持，缺失时同样显示“—”。

## 怎样控制额外开销

- 系统计数器与管道读取在原生后台线程进行，Flutter 读取缓存快照，约每 0.5 秒更新显示。
- 只有选定 FPS 程序后才启动 PresentMon；它没有可见控制台窗口，不向目标游戏注入代码。
- 只消费所选进程的帧记录，并关闭不需要的 GPU 时间和输入追踪；ETW 的底层图形事件仍有系统范围的采集开销，不能理解成完全零成本。
- 未开启监视器时，不启动计数器和 FPS 采集；关闭后释放计数器、停止辅助进程。正常退出先停止自己的 ETW 会话；强制终止程序时进程作业负责结束辅助进程，但不能保证系统 ETW 会话的正常清理。
- 使用独立的 ETW 会话名，正常停止不会关闭其他监控软件的会话。

Windows 可能要求管理员或性能日志权限。若权限被拒绝，设置会提示并提供管理员重启按钮，UAC 由用户确认。不同游戏、反作弊系统和呈现方式仍需实际验证，不保证覆盖所有游戏。

## 本机短测结果

2026-09-30 使用独立的 320×240 D3D11 测试窗口，以约 60 FPS 提交画面；各阶段预热 2 秒、测量 5 秒。CPU 采用进程累计 CPU 时间除以墙钟时间和逻辑处理器数量，内存为进程 Private Bytes。测试窗口自身的开销包含在主进程数据中，不能把这些数字当成整个 Flutter 音乐组件的占用。

| 阶段 | 测试主进程 CPU | 主进程私有内存 | FPS 辅助进程私有内存 |
| --- | --- | --- | --- |
| 监控关闭 | 0.117% | 52.13 MiB | 0 |
| 仅系统计数 | 0.215% | 57.44 MiB | 0 |
| 系统计数 + FPS | 0.507% | 57.56 MiB | 5.40 MiB |
| 再次关闭 | 0.195% | 57.25 MiB | 0 |

FPS 阶段读到约 59.63 FPS，GPU 读数约 5.12%，退出后确认辅助进程结束。辅助进程在该 5 秒窗口内记录的 CPU 增量为 0，属于短测的时间粒度结果，不表示它永远没有 CPU 开销。不同场景的图形事件数量、刷新率、驱动和后台程序会影响结果；这里不是游戏帧率损失测试，也没有实测完整应用的 GPU 或内存增量。

## 能否借用其他监控软件的数据

当前版本使用自己的 Windows 采集路径，没有接入 G-Helper 或 HWiNFO。仅打开另一款软件并不代表数据可被读取。查阅 G-Helper 的硬件与帧率采集相关实现，尚未发现面向第三方的公开数据接口；HWiNFO 提供共享内存机制，未来可以研究作为可选数据源，但需检查版本、许可及传感器可用性，也不意味着它提供游戏 FPS。

参考：[PresentMon CLI](https://github.com/GameTechDev/PresentMon/blob/main/README-ConsoleApplication.md)、[Windows GPU 使用率解释](https://devblogs.microsoft.com/directx/gpus-in-the-task-manager/)、[HWiNFO 共享内存](https://www.hwinfo.com/forum/threads/shared-memory-support.18/)。

## 启动生命周期回归

`tooling/performance_startup_probe.dart` 是单独的 Windows 测试入口，不是应用主入口。它使用真实 Flutter 引擎和原生通道，验证窗口创建后可以读取系统数据、CPU 时间会前进、移除监视器停止采集、重新开启后恢复，以及未启动的 FPS 目标不影响整机读数。可通过 `--fps-target=<可执行文件名>` 额外验证正在渲染的程序 FPS。

曾出现窗口创建前的 `Destroy → OnDestroy` 清理误永久停止监控服务，模拟通道的单元测试无法覆盖。修复后，服务只在 Flutter 窗口成功初始化后创建，真正销毁时释放；再次创建窗口会使用新的服务实例。回归测试在修复前复现了启动 8 秒后仍无系统读数的错误，修复后读取与开关流程通过。

测试入口会生成 `performance_startup_probe_result.json`，不会启动 MusicFetcher 或读取、修改用户设置。测试构建不要作为正式程序分发；正式构建使用默认的 `lib/main.dart`。

修复后的端到端测试还通过真实 Flutter 原生通道读到受控 D3D11 进程约 60.16 FPS，并取得 GPU 读数。目标窗口需实际呈现画面；本机将渲染测试窗口隐藏后没有有效帧事件，不能把这种情况当成采集代码异常。
